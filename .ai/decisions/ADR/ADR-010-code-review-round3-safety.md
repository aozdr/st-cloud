# ADR-010：第三轮代码复核的对象清理、Relay 恢复与分享缩略图安全边界

## 背景

第三轮复核发现三类跨模块风险：规范对象失败路径可能与并发成功请求竞争删除；relay 序号在远端分片失败前被提前确认；桌面端重启后无法证明 JVM 内存态 relay 的已提交边界。分享胶卷还需要在保留分享授权语义的前提下避免直接把原图流作为缩略图资源。

## 决策

1. 规范对象失败只写入持久化孤儿候选。候选经过宽限期后，必须同时确认没有 NORMAL `file_object`、有效 `file_node` 引用和活动 `upload_session`，才允许在事务外删除对象。
2. relay 使用 `committedSeq` 与 `inFlightSeq`。严格连续序号在 body、追加和远端 part 完整成功后提交；无法证明远端状态时显式 abort，不把失败请求标为成功。
3. 桌面端持久化 relay 模式、块大小和限速元数据。应用重启后 relay 任务进入 restart-required，禁止切换到普通 chunk URL、PUT 或 merge。
4. 分享胶卷使用分享模块的授权缩略图 endpoint，复用密码、验证码、过期、下载开关和范围校验，只输出图片 JPEG 缩略图，原下载计数不因胶卷请求增加。

## 放弃的方案

- 在失败路径立即删除规范对象：无法覆盖并发成功请求和跨实例竞态。
- 失败后把 relay 自动切换为普通直传：会绕过已提交边界，可能造成重复或错序写入。
- 让前端直接复用原分享 `/stream` 作为胶卷：会把缩略图 UI 资源和原文件下载语义混在一起。

## 理由

持久化候选和删除前复核提供跨实例安全边界；relay 的显式提交状态比请求到达状态更接近真实远端结果；重启后重新开始是可证明的安全策略；缩略图由分享服务统一鉴权可避免前端绕过分享范围。

## 后续限制

- relay 仍依赖 JVM 内存会话，多实例部署需要粘性路由或共享状态。
- 首次缩略图生成是同步缓存路径，后续可按运维需要增加异步预热和击穿保护。
