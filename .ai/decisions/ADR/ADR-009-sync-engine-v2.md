# ADR-009：同步引擎 V2（版本门控 + 游标增量 + 冲突副本登记）

> 架构决策记录。存放于 `.ai/decisions/ADR/`，编号递增。由 Knowledge Manager 复核一致性。

## 状态

Accepted

## 背景

桌面端同步引擎存在自激死循环：每次启动无条件全量对账；keep_both 冲突处理把云端版本下载成 `(冲突-时间戳)` 副本却不登记 sync_state，被监听器当作新文件上传回云端；`(本地-时间戳)` 临时文件在同步目录内删除触发反向删云端；冲突处理后 `local_mtime` 被整行覆盖为 NULL 导致反复上传；服务端同目录移动/同名重命名产生 `old==new` 的 MOVE 脏日志。用户要求以“版本号 + 最后同步时间”控制全量同步，并整体重构。

## 决策

1. **全量门控**：客户端 `sync_config.sync_version` 与引擎常量比对；不一致或 `last_sync_at` 为空 → 全量重建一次（清本地垃圾 → 清表（保留游标）→ 云端快照对账），完整成功才固化版本；日常启动只走增量。
2. **增量范围**：以 `sync_change_log.id` 单调游标为准，游标仅在全部变更处理成功后推进；不做时间戳过滤（避免时钟漂移漏变更）。
3. **防自激**：引擎写入路径 30s TTL + sync_state mtime 比对；冲突副本落盘即登记；本地版副本经系统临时目录上传。
4. **状态持久化**：`upsertSyncState` 改合并语义（COALESCE），未传字段保留，禁止擦除 `local_mtime`。
5. **服务端守卫**：rename 同名 / move 同目录 no-op；delta 过滤 `oldPath == path`。
6. **异常数据清理**：`POST /api/admin/sync/cleanup-junk`（ADMIN），复用回收站永久删除逻辑（引用归零删 S3、退还配额、清 ES、清 sync_change_log）。

## 放弃的方案

- **最小补丁**：保留旧架构逐点修补（状态擦除/临时文件/事件丢失）。放弃原因：根因是状态模型与自激反馈，打补丁无法保证不再复发。
- **服务端 `sinceTime` 时间过滤**：用最后同步时间过滤 delta。放弃原因：客户端/服务端时钟漂移会导致漏变更；游标单调精确，时间只做门控条件。
- **每次启动全量对账**（现状）：成本高且是死循环的触发面，废弃。

## 理由

- 游标 + journal 是 Dropbox/Syncthing 等主流实现的共识模型，单调精确、断网可恢复、不重不丢。
- 合并语义从根上消除“局部更新擦状态”类缺陷，防御面大于单点修复。
- 清理复用既有永久删除链路，避免重复实现 S3/引用/配额逻辑，降低误删风险。

## 后续限制

- 每次同步逻辑变更需递增 `SYNC_ENGINE_VERSION`，否则不会触发一次全量重建。
- `(本地-时间戳)` 副本上传失败不自动重试（保留 conflict 标记，用户再编辑即重试）；如需自动重试，后续增加 `pendingLocalCopy` 状态字段。
- 服务端需部署新代码后清理接口才可用；桌面端需重新打包安装。
