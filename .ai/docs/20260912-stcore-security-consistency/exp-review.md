# 体验评审

## 1. 评审范围

本任务不改变页面布局和视觉系统，影响集中在上传入口、错误状态和团队/个人 API 边界。评审对象是 `st-web` 的 `useUpload`、团队空间上传上下文和 `st-desktop` 上传恢复流程。

## 2. 评审结论

| 项目 | 结论 |
|---|---|
| 页面结构 | 保持现有个人文件页、团队空间页、上传队列和同步任务页 |
| 组件 | 复用现有上传队列、Toast、错误提示和加载状态，不新增视觉组件 |
| 数据流 | 个人请求使用 `/file/upload/*`；团队请求使用 `/team/{spaceId}/files/upload/*` |
| 状态管理 | 保留现有 hashing/pending/uploading/merging/completed/failed/paused 状态；新增 session-expired/conflict/limit 的错误分类 |
| 可理解性 | 错误提示区分无权限、会话失效、参数错误、名称冲突和资源超限 |
| 无障碍 | 不改变键盘操作、焦点、颜色和字号；错误提示继续使用现有可读文本组件 |

## 3. 体验要求

- 团队上传必须从当前团队空间上下文取得 `spaceId`，不得由用户在个人上传表单中手填。
- 个人入口携带 team `spaceId` 时显示明确失败，不自动切换到其他空间。
- uploadId 失效时停止自动重试，提示用户重新开始上传；不能循环请求状态接口。
- 旧客户端仍发送 `s3UploadId/fileId` 时不改变 UI；服务端以 session 为准。
- 同名或乐观锁冲突时保留文件列表和上传队列状态，提示刷新/重试，不显示“上传成功”。
- 文件夹大小返回 `complete=false` 时显示“统计不完整”或重试入口，不显示精确总量。
- ZIP/Archive 超限在写入响应或创建解压任务前反馈，不让用户等待后才得到失败。

## 4. 交互验收

- 团队空间上传、断点续传、合并、中止和中转流程均能在显式团队命名空间下完成。
- 个人空间上传仍可使用原接口。
- 权限失败、会话失效、冲突和资源上限均有非空错误提示。
- 不泄露其他用户的文件名、路径、nodeId、spaceId 或 S3 uploadId。

## 5. 评审结论

无视觉设计阻塞，允许进入后端架构和接口设计；实现时必须保持上述 API 状态语义。

## 6. 遗留问题点

无。个人/团队入口、错误状态和无视觉改动范围已由用户确认。
