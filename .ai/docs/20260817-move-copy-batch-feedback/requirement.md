# 需求文档：批量移动/复制的结果反馈与重名策略统一

# 一、需求概述

## 1.1 功能名称

批量移动/复制的结果反馈与重名策略统一

## 1.2 背景说明

已核验代码，现状存在两个问题：

1. **批量移动遇重名整批回滚**：`FileServiceImpl.move` 与 `moveTeamFiles` 在 `@Transactional` 循环内对目标目录重名直接抛 `FILE_ALREADY_EXISTS`，整个批次回滚。用户批量移动 10 个文件，只要 1 个重名，全部失败。
2. **语义不一致**：`copy` / `copyTeamFiles` 使用 `resolveNameConflict` 自动追加序号（如 `a (1).txt`）继续执行；移动却直接失败。
3. **前端无逐项反馈**：`FileBrowser` 拖拽移动与 `MoveDialog` 只有成功/失败 toast，用户不知道哪个文件失败、失败原因是什么。

## 1.3 用户角色

| 用户角色 | 权限 | 使用场景 |
|---------|------|---------|
| 个人用户 | 自有文件管理 | 批量整理文件，移动/复制到目标目录 |
| 团队空间成员 | 团队目录权限 | 团队空间批量移动/复制文件 |

# 二、业务需求分析

## 2.1 用户故事

- 作为个人用户，我希望批量移动文件到目标目录时重名文件自动改名而不是整批失败，从而一次完成整理。
- 作为团队空间成员，我希望移动/复制后看到每个文件的结果（成功/自动改名/失败原因），从而知道下一步处理什么。

## 2.2 功能列表

| 编号 | 功能 | 描述 | 优先级 |
|------|------|------|--------|
| F1 | 移动重名自动改名 | `move` / `moveTeamFiles` 复用 `resolveNameConflict`，与复制行为一致 | P0 |
| F2 | 逐项结果返回 | move/copy（个人+团队）返回每项 `nodeId / 原名称 / 最终名称 / 状态 / 原因`；单项失败不整批回滚 | P0 |
| F3 | 前端结果反馈 | 移动/复制完成后展示结果明细（成功数、自动改名项、失败项原因） | P0 |
| F4 | 非法目标整体拒绝 | 移动到自身/子孙目录仍为整体参数错误，整批拒绝 | P1 |

## 2.3 业务流程

```
用户选择 N 个文件 → 选择目标目录 → 确认移动/复制
   ↓
后端逐项校验处理：重名→自动改名；非法目标→整体拒绝；单项异常→收集原因
   ↓
返回 MoveCopyResultVO 列表（每项：nodeId、原名称、最终名称、status、reason）
   ↓
前端展示结果：成功 N 项（含自动改名提示）、失败 M 项（原因），可选重试
```

# 三、功能边界

## 包含范围

- 个人文件 move/copy、团队文件 move/copy 四个入口
- 批量逐项处理与结果收集
- 前端 MoveDialog 与拖拽移动的结果反馈

## 不包含范围

- 覆盖模式（同名覆盖已有文件）
- 跨用户/跨租户移动复制
- 回收站恢复逻辑（已实现冲突处理，本次不动）

# 四、业务规则

- 重名：目标目录存在同名 → 自动生成唯一名（复用 `generateUniqueName`，规则 `name (1).ext`），不覆盖
- 移动到自身/子孙目录：整体拒绝（参数错误），不逐项
- 权限：沿用现有 `getNodeByIdAndOwner` / `validateTeamNode` 校验，越权或不存在项标记 FAILED 并记录原因
- 事务：成功项提交，失败项不影响成功项（不再整体回滚）
- 返回结构：`MoveCopyResultVO { nodeId, originalName, finalName, status: SUCCESS|RENAMED|FAILED, reason }`

# 五、异常场景

| 场景 | 处理方式 |
|------|---------|
| 目标目录不存在/无权限 | 整体参数错误，整批拒绝 |
| 移动到自身/子孙目录 | 整体拒绝 |
| 单项重名 | 自动改名，status=RENAMED |
| 单项正在编辑 | 该项 FAILED，reason=FILE_EDITING（按 P1 裁决） |
| 单项越权/不存在 | 该项 FAILED，reason=NOT_FOUND / FORBIDDEN |

# 六、非功能需求

## 性能

- 单次批量上限 100 个节点（参数校验）
- 重名计数复用现有 `countByParentAndName`，不引入明显 N+1 放大

## 安全

- 沿用现有权限校验；返回结果不泄露他人数据

## 可维护性

- 服务层返回逐项结果，Controller 仅透传；新增 DTO 复用现有 `Result` 封装

# 七、验收标准

- Given：目标目录已有 `a.txt`，用户批量移动 `[a.txt, b.txt]`；When：确认移动；Then：`a.txt` 自动改名为 `a (1).txt`，`b.txt` 正常移动，接口返回 SUCCESS/RENAMED 两项，前端展示结果
- Given：用户选择移动到文件夹自身；When：确认；Then：整体拒绝，无部分执行
- Given：正在编辑的文件参与批量移动；When：确认；Then：该文件项 FAILED 且原因明确，其余项成功（按 P1 裁决）
- Given：团队空间文件批量复制到重名目录；When：确认；Then：自动改名并返回最终名称
- 构建：`mvn test`（st-core 新增单测全绿）+ `npm run build` 通过

# 八、遗留问题点（Grill Me 拷打收敛）

| 编号 | 遗留问题 | 影响 | 建议方案 | 用户裁决 |
|------|---------|------|---------|---------|
| P1 | 单项失败语义：编辑保护/越权等单项失败时，成功项照常提交还是整批回滚 | 决定事务边界与回滚复杂度 | 成功项提交、失败项收集原因并返回明细（更符合批量操作直觉） | 待确认 |
| P2 | 自动改名的可见性：移动/复制重名自动改名后是否需要醒目提示 | 用户可能找不到改名后的文件 | 结果列表明确展示 RENAMED 项（原名称 → 新名称） | 待确认 |
| P3 | 拖拽移动的结果反馈形态：toast 摘要还是完整弹层 | 影响交互复杂度 | 拖拽用 toast 摘要（"成功 3，改名 1，失败 1"）+ 失败项可点击展开 | 待确认 |

# 九、风险分析

| 风险 | 影响 | 解决方案 |
|------|------|---------|
| 事务边界调整引入部分提交 | 出现中间态 | 设计阶段定版逐项事务策略（REQUIRES_NEW 或同事务收集异常不回滚） |
| 前端改动影响既有 MoveDialog | 回归 | 复用现有对话框，仅新增结果展示区 |
| 移动/复制行为统一为自动改名 | 与旧行为差异 | 结果明细明确提示改名项 |

# 附：V15 流程验证说明

本需求用于验证 V15 worktree 隔离流程，实现阶段拆分为并行批次（文件零重叠）：

- BE-01：`st-core` `FileService` / `FileServiceImpl`（重名自动改名 + 逐项结果收集 + 单元测试）
- BE-02：`st-core` `FileController` / `TeamController` + `MoveCopyResultVO`（接口透传 + 参数校验 + 单元测试）
- FE-01：`st-web` `FileBrowser.tsx` / `MoveDialog`（结果展示与拖拽摘要）
