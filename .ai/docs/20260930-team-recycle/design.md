# 团队回收站修复设计

revision: team-recycle-design-v1

目标和场景：团队文件夹调用 deleteTeamFiles 后自身 status=1，子孙保持 status=0 并由祖先状态拦截。现有回收列表排除了全部 space_id>0 节点，恢复入口 getNodeByIdAndOwner 也拒绝团队节点。修复现有回收站业务，页面布局与请求地址不变。

用户决策：2026-09-30 用户选择“空间拥有者和管理员可查看、恢复（推荐）”。管理员指空间内有效 role=0 成员；空间拥有者仍需有效成员关系。有效关系必须同租户、空间正常未删除、成员未删除未过期；外部成员还要求允许外部协作。普通成员不能凭上传者/文件 owner 身份绕过。此规则同样约束已有永久删除和清空入口。

方案：TeamStorageMapper 按显式 tenant/user 即时查询可管理的空间 ID，避免 core 反向依赖 team。列表在同租户内查询“当前用户个人节点 OR 授权团队空间节点”的回收态记录。写入口使用独立回收核权函数，个人仍严格 owner、团队严格管理空间。恢复保留 space_id，团队父节点只需同 tenant/space 且祖先正常，不要求同 owner；无可用父节点回到相同空间的根目录。团队重名以整个空间判断；子孙路径及恢复事件保留空间并覆盖不同上传者。独立回收的子节点不随父节点恢复。永久删除递归按 tenant/space，个人按 tenant/owner/personal，不能漏掉团队其他 owner 的子节点；非回收根不得永久删除。清空仅选同一授权列表，个人配额与团队配额按既有逻辑释放。写事务 RC，授权查询不使用共享缓存，S3 删除仍提交后异步事件。

边界：没有团队专用新页面，不给普通成员或系统 ADMIN 增加成员关系旁路，不变更生产表、状态值、保存时长与正常个人文件接口；自动到期清理沿用系统职责。H2 测试 schema 仅补齐生产既有 team_member/team_external_config 表，新增迁移不适用。API 路径/响应字段兼容，列表新增授权的团队回收项。

验证：H2 和真实本机独立 MySQL 运行目录删除→回收列表→恢复、混合 owner、父目录失效/重名、失权/过期/禁用/跨空间/跨租户、永久删除与配额、清空隔离及个人回归。真实 MySQL 的测试事务自动回滚。单独启动完整 st-api，连接独立库和现有健康 Docker Redis/MQ/RustFS/ES，使用真实 HTTP、JWT、数据库；只创建本任务唯一数据，不操作用户文件。明确区分模拟外部组件测试与完整 HTTP 验证，记录退出码和日志。

风险：团队删除路径已经存在，补列出后必须同步恢复/删除核权，否则可见但不可操作。同名恢复不可查询个人范围；混合 owner 的团队子树不可按 root owner 筛选。基础设施异常必须使请求失败，不能回退为空列表或扩大权限。

未决问题：无。配置/权限方案已确定，无需额外确认。
