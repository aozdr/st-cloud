# CR-01 令牌撤权测试用例

来源：[需求](../20260924-code-review-design/CR-01/requirement.md)、[设计](../20260924-code-review-design/CR-01/design.md)。全部 NOT RUN。使用总册 T1/U1/U2/T2/U3；为 U1 创建权限角色 R，登录得到 Access A0、Refresh F0，记录数据库版本 v。除指定场景外每次管理写入都等待提交后再发起鉴权。建议后续采用 Spring 集成、真实 MySQL 并发、Redis CAS、WS 集成；本轮不执行。

| ID / 优先级 / 映射 | 前置条件与步骤 | 预期结果与证据 |
|---|---|---|
| TC01-01 / P0 / A01-1 | 分别禁用、逻辑删除、重置 U1 密码；提交后用 A0 请求受保护接口、用 F0 刷新。 | 两种旧令牌均不能获得授权；数据库变更与版本递增同事务；重置后旧密码失败、新密码可正常登录。保存版本与认证轨迹。 |
| TC01-02 / P0 / A01-2 | 分别撤销 U1 的 ADMIN、重新分配普通角色、删除所持角色。 | U1 旧令牌失效；新登录权限与提交后数据一致，不残留 ADMIN。无关 U2 版本和会话不变。 |
| TC01-03 / P0 / A01-2 | R 关联多名用户，其中部分不在线；分别删除权限、禁用角色、改变 dataScope。 | 全部受影响用户版本递增，提交后的旧令牌拒绝；无关角色用户不被撤权；同一事务不遗漏部分用户。 |
| TC01-04 / P1 / A01-3 | 只修改昵称或配额，保持安全字段不变；再次用 A0 访问。 | 版本不因非安全字段单独递增，A0 仍有效；对应字段保存正确。 |
| TC01-05 / P0 / R01-1 | 在修改关联或密码之后、事务提交之前注入数据库异常。 | 业务字段和版本一起回滚，旧会话仍与回滚后状态匹配；不得出现权限已改但版本未变的部分提交。 |
| TC01-06 / P0 / R01-2 | 构造测试密钥签名的令牌，分别使用错租户、不存在用户、已删除用户、禁用租户、删除租户。 | 全部拒绝，不建立 UserContext/TenantContext；不能因签名合法而越租户。 |
| TC01-07 / P0 / R01-7 | 分别提交缺失、负值、溢出、小数、非数字 securityVersion 的 Access/Refresh；再使用合法整数版本。 | 非法版本全部拒绝，缺失不按 0；合法版本正常。每个输入独立记录，不能只测过期值。 |
| TC01-08 / P0 / R01-4 | A0 合法，令安全版本主库查询超时或抛错；恢复后重试。 | 故障时拒绝业务访问，无陈旧缓存兜底；恢复后合法令牌可用；记录未访问副本/旧缓存的证据。 |
| TC01-09 / P0 / A01-5 | 以 refresh、download、editor、未知 type 令牌请求普通 HTTP 与 WS 握手；另用流令牌访问正确和错误节点/端点。 | 非 Access 不进入普通授权/WS；流令牌只满足原端点、节点、用途及期限约束，不能扩权。 |
| TC01-10 / P1 / R01-2 | 合法认证后令下游抛异常，再复用执行线程处理另一用户和匿名请求。 | finally 清理用户/租户上下文，后续请求不能继承 U1 权限；正常 Access 的签名与到期检查保持有效。 |
| TC01-11 / P0 / A01-4 | 同一 F0 同时发送两次刷新，在 Redis 比较替换处汇合后并行继续。 | 只有一次 CAS 成功并返回有效新令牌；另一次明确失败，旧 F0 不可再用。记录 Redis 最终登记值与两次响应。 |
| TC01-12 / P0 / A01-4、Review | 刷新通过初次 isCurrent 后暂停；另一事务改密/撤权提交使版本 v→v+1；恢复刷新读取用户。 | 旧 F0 不得继承 v+1 签发有效会话；响应拒绝且不能覆盖新会话登记。检查签发调用/返回值及版本。 |
| TC01-13 / P0 / A01-4、Review | 刷新完成最后版本检查后暂停；撤权提交，再恢复签名和 CAS；分别尝试返回的 Access 与 Refresh。 | 即使产生令牌，其版本仍为旧 v，后续鉴权/刷新拒绝；不会出现旧权限配新版本。另覆盖 revoke 发生在 CAS 前的比较失败。 |
| TC01-14 / P0 / R01-3 | 登录在读取用户、角色、权限的交界处暂停；并发撤权提交后恢复登录。 | 签发快照的权限和版本一致；允许签发旧版本随后被拒绝，不允许旧权限配可通过认证的新版本。 |
| TC01-15 / P0 / R01-1 | 用户分配 R 与修改/删除 R 权限并发，使用两种先后持锁顺序。 | 最终成员集合、角色权限、用户版本一致；提交后旧会话均不能利用撤回的权限；无漏递增和部分提交。 |
| TC01-16 / P0 / A01-4 | 安全变更提交后使 Redis revoke 失败；用旧 Access/Refresh 请求另一应用实例。 | 数据库版本仍使两者失效，不依赖 Redis 清理成功；故障日志不泄露令牌。 |
| TC01-17 / P0 / Review | 管理更新 A 在读取旧用户后暂停；B 重置密码并提交；A 仅改昵称/配额后继续提交。 | B 的新密码及版本保留，旧密码不能登录；A 只更新声明字段，不回写旧 password/status。 |
| TC01-18 / P0 / Review | A 读取旧状态后暂停；B 禁用用户并提交；A 分别执行仅改昵称、显式重新启用两种请求。 | 仅改昵称保持禁用；显式启用基于锁后最新状态递增版本，不能复活禁用前的令牌。保存两事务交错和最终行。 |
| TC01-19 / P0 / A01-5 | A0 建 WS 后撤权；分别触发接收消息、sendToUser、sendToTenantUser。 | 每条业务消息前复核失败并关闭连接/清理注册表；旧连接不再收发业务数据。 |
| TC01-20 / P0 / A01-5 | 建立 WS 后推进可控时钟至 Access 过期；另用已过期/缺版本令牌握手。 | 旧连接下一次收发前关闭；非法握手拒绝；不因长连接绕过到期或升级重新登录要求。 |
| TC01-21 / P0 / A01-1、A01-3 | 两实例共享主库：实例 A 提交撤权后由实例 B 发起全新认证；另保留提交前已完成鉴权的在途请求。 | B 必须拒绝旧令牌；在途请求不要求中途强制撤销，与定义的提交边界一致。 |
| TC01-22 / P1 / R01-3 | 注册/新建用户事务分别成功和回滚；在提交边界观察令牌和 Redis 登记。 | 不为未提交/回滚用户产生可用会话；成功用户有初始化版本与一致权限。 |

执行时关联现有 AuthServiceIntegrationTest、JwtUtilsTest、管理服务及 WS 测试作为实现入口，不预设现有测试已覆盖上述交错。
