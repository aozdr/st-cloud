# 一、需求概述

## 1.1 功能名称

在线文档编辑（OnlyOffice 社区版集成）

## 1.2 背景说明

- 当前 docx/xlsx/pptx 只能只读预览（docx-preview 渲染，复杂排版走样）
- 主流网盘（百度网盘/阿里云盘/坚果云/Nextcloud）均提供在线编辑
- OnlyOffice 社区版免费开源（AGPLv3），Docker 自托管，无付费依赖

## 1.3 用户角色

| 用户角色 | 权限 | 使用场景 |
|---------|------|---------|
| 个人用户 | 本人文件可编辑 | 在线改文档、表格、演示稿 |
| 团队用户 | 按文件夹权限/角色判断 | 团队文件在线编辑、多人协同 |
| 分享访客 | 按分享权限判断 | 有上传/编辑权限时可编辑 |
| 管理员 | 部署与配置 | 部署 OnlyOffice 容器、配置地址与密钥 |

# 二、业务需求分析

## 2.1 用户故事

- 作为个人用户，我希望在网盘里直接编辑 Word/Excel/PPT，从而不用下载-编辑-回传
- 作为团队编辑者，我希望和同事同时编辑一份文档，从而减少来回传文件
- 作为管理员，我希望 One 命令启动编辑服务，从而不增加运维负担

## 2.2 功能列表

| 编号 | 功能 | 描述 | 优先级 |
|------|------|------|--------|
| F1 | 打开编辑器 | docx/xlsx/pptx 点击「在线编辑」进入 OnlyOffice 编辑器 | P0 |
| F2 | 编辑与保存 | 编辑内容保存回原文件，生成 file_version 可回滚 | P0 |
| F3 | 只读打开 | 无编辑权限时以只读模式打开（下载/打印按权限） | P0 |
| F4 | 权限映射 | 编辑权限判定：个人 owner / 团队文件夹权限 / 分享权限 | P0 |
| F5 | 多人协同 | OnlyOffice 原生协同编辑，平台保证不丢数据 | P1 |
| F6 | 文件保护 | 编辑期间禁止删除/移动/重命名该文件 | P0 |
| F7 | 部署与配置 | docker-compose 内置 onlyoffice 容器 | P0 |

## 2.3 业务流程

```
用户点击「在线编辑」
   ↓
后端校验权限（个人/团队/分享）
   ↓
生成 OnlyOffice config（document.url + key + permissions + callbackUrl + JWT）
   ↓
前端 iframe 打开 OnlyOffice 编辑器
   ↓
用户编辑 → OnlyOffice 自动保存 → 回调后端
   ↓
后端校验回调签名 → 保存新版本 → 更新索引/同步/配额
```

# 三、功能边界

## 包含范围

- docx/xlsx/pptx 在线编辑；pdf/csv/txt 等 OnlyOffice 支持的格式只读打开
- 复用现有权限体系（不新增权限点）：编辑判定 = 具备 upload 能力（个人 owner / 团队 upload / 分享 upload）
- 保存复用现有版本机制与事件链路（FileIndexEvent / SyncChangeEvent / 配额差值）
- 桌面端 WebView 与移动端 PWA 通过浏览器直接可用

## 不包含范围

- 不购买 OnlyOffice 企业版/托管服务，不做集群与品牌定制；不支持外部实例配置（用户裁决：仅内置）
- 不新增数据库表；不修改 team_role / team_folder_permission / file_share 权限模型结构
- 不做 OnlyOffice 自身的宏、表单高级功能定制
- 不实现原生 App 独立编辑器（走 WebView）

# 四、业务规则

- 可编辑判定：个人文件 owner 可编辑；团队文件按文件夹权限/角色 permissions 含 upload；分享文件按分享 permissions 含 upload
- 只读场景：无 upload 权限时打开为只读（view/download 按既有权限）
- 回调安全：OnlyOffice 回调必须携带签名（JWT/secret 校验），后端校验通过才落盘，防止越权覆盖
- 文档 URL：使用短期 download-token，避免长期直链泄露
- 版本：保存回调落盘时生成新 file_version（策略见遗留问题点 P1）
- 文件保护：编辑打开期间（含多人协同）该文件禁止删除/移动/重命名（复用文件锁检查）
- 格式不支持：非 OnlyOffice 支持格式点击「在线编辑」提示不可用，不进入编辑器

# 五、异常场景

| 场景 | 处理方式 |
|------|---------|
| OnlyOffice 服务不可达 | 提示「编辑服务暂不可用」，回退只读预览 |
| 回调签名无效 | 拒绝落盘，记录审计日志 |
| 编辑时文件被并发操作（删除/移动） | 文件锁拦截，提示先关闭编辑器 |
| 保存时文件被他人覆盖 | OnlyOffice 协同/版本机制保留两份内容（按 P2 方案） |
| 权限不足点编辑 | 按钮隐藏/禁用，打开只读 |

# 六、非功能需求

## 性能

- 编辑器首屏加载 ≤5s（局域网/公网同机房）
- OnlyOffice 容器资源：建议 2 核 2GB（单机部署前提，见 P3）

## 安全

- 回调签名校验，防伪造回调覆盖任意文件
- 文档 URL 短期有效；编辑 token 与用户/文件绑定
- 越权矩阵：无 upload 权限者不能发起编辑、不能伪造保存

## 可维护性

- 全部配置集中在 application.yml（stcloud.onlyoffice.*）
- docker-compose 一键起停；OnlyOffice 可换外部实例地址

# 七、验收标准

- Given 我是文件 owner，When 点击在线编辑，Then 打开可编辑的 OnlyOffice 编辑器并可保存
- Given 编辑后保存，When 回调落盘完成，Then file_version 新增一条且文件内容为最新版
- Given 我只有查看权限，When 点击在线编辑，Then 打开只读模式，无编辑按钮
- Given 文件正在被编辑，When 他人尝试删除/移动/重命名，Then 操作被拒绝
- Given 伪造回调，When 提交无签名请求，Then 服务拒绝落盘并记录审计

# 八、遗留问题点（Grill Me 拷打收敛）

| 编号 | 遗留问题 | 影响 | 建议方案 | 用户裁决 |

| P3 | 部署形态与资源：内置容器占约 2GB 内存 | 部署与环境差异 | docker-compose 内置 onlyoffice 容器 | ✅ 只内置，不做外部实例配置（20260815 用户确认） |

# 九、风险分析

| 风险 | 影响 | 解决方案 |
|------|------|---------|
| OnlyOffice 与业务鉴权模型差异导致越权 | 文件泄露/被覆盖 | 回调签名校验 + 服务端权限判定 + 审计 |
| 容器资源不足 | 编辑服务不稳定 | 明确 2GB 前提，P3 支持外部实例 |
| 版本膨胀 | 存储成本上升 | P1 版本上限策略 |
