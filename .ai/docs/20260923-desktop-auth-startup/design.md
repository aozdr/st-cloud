# PC 端启动登录态恢复设计

## 目标、用户与场景

用户重开 PC 客户端后，access token 随窗口 session 结束而消失，refresh token 仍在本地。现有路由把 refresh token 当作已完成认证，立即挂载主页、侧栏和文件列表；并发业务请求先返回 401，随后拦截器才刷新令牌。启动时应先恢复有效会话，再加载业务页面。

## 边界与规则

- 受保护路由增加“会话恢复中”状态。仅有 refresh token、或 access token 已过期时，不挂载其子页面。
- 恢复动作只提交一次；React 开发模式重复执行 effect 时复用同一 Promise。
- access token 有效时直接进入页面；无 token 时直接进入登录页。
- 刷新成功后原子更新两种 token、同步 Electron 主进程认证并放行页面；失败时清理两种 token、用户状态和认证标记，转到登录页。
- 页面内正常运行阶段仍保留现有 401 拦截器兜底与主动刷新定时器。

## 异常、数据与 API

- 复用现有 `POST /api/auth/refresh`，响应结构不变，无服务端或数据库修改。
- 恢复请求使用不带业务拦截器的 HTTP 客户端，避免刷新接口自身 401 时递归触发 401 拦截器。
- 网络异常与 refresh token 失效目前统一回登录页；不引入离线会话能力。

## 风险与验证

认证门禁错误可能导致启动卡住或误进入受保护页。验证有效/无效 refresh token、有/无 access token、开发模式重复挂载、现有登录路径及构建。无待用户裁决的范围、兼容性或风险问题。
