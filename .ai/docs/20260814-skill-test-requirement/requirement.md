## 0. Grill Me 拷打问题清单（7 问）

> Grill Me 目标：对原始需求进行不留情面的拷打，先质疑"用户是谁、痛点是否真实、现有方案为何不够、最小可用范围、边界与异常、权限语义"，再进入 PRD 结构。

**原始需求**：给团队空间的文件/文件夹加"权限配置"功能。管理员可以在文件详情里设置权限，可以针对全体成员（管理员除外）或单独用户配置权限；配置后该用户在该文件夹及子文件的有效权限 = 角色权限 + 配置权限（增强）。分享出去的文件权限不能超过配置权限。

| # | 拷打问题 | 澄清结论 |
|---|---------|---------|
| Q1 | **用户是谁？谁操作、谁被影响？** | 操作者：团队空间管理员（空间拥有者 roleId=0 或持有 `manage_settings` 权限点）；被配置主体：全体成员（管理员除外）或单独用户；实际生效对象：所有团队成员在文件夹/文件上的操作。前端操作入口在管理员一侧，权限校验在后端统一执行。 |
| Q2 | **真实痛点是什么？现状哪里不够？** | 现有 `file_share.permission` 为单值枚举（0-查看/1-下载/2-上传/3-编辑），团队文件夹权限为单值（-1/0/1/2），无法表达"角色 = 权限点组合"与"按文件夹/用户维度增强"。典型场景：某成员是"上传者"角色（仅查看+上传），管理员希望该成员在**某个项目文件夹内**还能下载——现有模型只能全局改角色或不做，无法按文件夹局部授权。 |
| Q3 | **为什么不能靠改角色或分享代替？** | 改角色是空间级全局变更，影响该角色下所有成员与所有文件夹，粒度太粗；分享是临时、逐文件、依赖分享者手动操作，无法形成持久、继承、按节点管理的规则。文件夹权限配置需要的是持久化 + 子树继承 + 按节点管理的授权规则。 |
| Q4 | **最小可用范围（MVP）是什么？** | 管理员在文件/文件夹详情配置权限；主体支持 `all`（全体非管理员）与 `member`（单用户）；权限集从 9 个权限点勾选；有效权限 = 空间角色权限 ∪ 命中文件夹规则权限（并集增强）；分享权限 ⊆ 分享者对该文件的有效权限。`role` 主体（按角色配置）作为二期扩展。 |
| Q5 | **权限语义：只增强还是允许显式禁止？** | 仅增强（并集），不做显式禁止（design.md 已确认）。理由：心智模型简单，避免"禁止"与角色权限冲突的裁决复杂性；未来若需要"禁止下载"等场景，作为独立增强项评估，不进入本次范围。 |
| Q6 | **边界与异常：管理员、all 规则、子树继承怎么处理？** | 管理员（roleId=0 或 `manage_settings=true`）直接获得全部权限，不受文件夹规则限制；`all` 规则明确排除管理员；规则可挂在任意节点（文件夹或文件），经父链向上收集后对该节点及子树生效；同一用户命中多条规则取**并集**；`upload` / `download` 隐含 `view`，计算时自动补全。 |
| Q7 | **分享权限超限怎么处理：拒绝还是自动裁剪？** | 拒绝 + 明确提示（"分享权限不能超过你的权限"），避免静默裁剪造成用户误解；发起分享前置需要 `share` 权限点（design.md 已确认）。 |

## 1. 执行摘要

为团队空间增加**文件夹/文件权限配置**能力：管理员可在文件或文件夹详情中对"全体成员（管理员除外）"或"单独用户"配置权限点集合；用户对节点及其子文件的有效权限 = 空间角色权限 ∪ 命中的文件夹规则权限（并集增强）；分享出去的权限不得超过分享者对该文件的有效权限。该能力将现有的单值权限模型升级为"角色权限点组合 + 文件夹规则增强 + 分享权限上限"三层语义，解决"按文件夹局部授权"与"分享越权"两个核心问题。

---

## 2. 问题陈述

### 谁有这个问题
- 团队空间管理员：需要把"下载/编辑"等能力按文件夹精准授予某些成员，但受限于全局角色模型，做不到局部授权。
- 团队成员：被"全局角色"一刀切，无法按项目文件夹获得差异化权限。
- 文件分享者与接收者：分享权限缺少"不得超过自身权限"的硬约束，存在越权分享风险。

### 问题是什么
- 权限粒度不足：`file_share.permission`（0/1/2/3）与文件夹权限（-1/0/1/2）均为单值枚举，无法表达权限点组合（如"查看+上传"）。
- 无文件夹级规则：管理员无法针对"某个文件夹 + 某类主体"配置权限。
- 分享越权无拦截：分享权限未与分享者对该文件的有效权限做包含校验。

### 为什么痛苦
- **管理侧**：临时放开某成员的下载权限只能改全局角色，影响面大、易出错、不敢改。
- **安全侧**：分享权限可超出自身权限，存在数据泄露隐患（云盘专项规则重点关注分享访问控制）。
- **一致性侧**：角色、文件夹、分享三套权限语义各自为政，用户心智与实现都混乱。

### 证据 / 依据
- `.ai/docs/20260814-permission-model/design.md`：明确指出现有模型"未体现角色=权限组合与文件夹权限增强语义"，并给出确认后的权限点体系、角色模型、并集增强与分享上限方案。
- 项目既有约束：文件权限安全、分享访问控制为云盘专项重点关注项。

## 3. 目标用户与画像

### 主要画像：团队管理员（Admin）
- 角色：空间拥有者或持有 `manage_settings` 权限点的管理成员。
- 目标：按文件夹/文件精准控制成员权限，不惊动全局角色。
- 痛点：只能全局改角色；对"某成员在某个项目文件夹内可下载"这类诉求无能为力。
- 行为：在文件/文件夹详情打开"权限配置"，选择主体（全体/单用户），勾选权限点保存。

### 次要画像：团队成员（Member）
- 角色：被配置对象，持有空间角色（内置查看者/编辑者或自定义角色）。
- 目标：在授权文件夹内获得增强权限（如额外下载），未配置的文件夹保持角色权限。
- 痛点：权限来源不透明，不知道自己在某文件夹"能做什么"。

### 次要画像：文件分享者（Sharer）
- 角色：发起分享的成员。
- 目标：把文件分享给外部/内部人员，但分享权限不超出自己对文件的有效权限。
- 痛点：当前分享可配置超出自身权限的权限，造成越权风险。

## 4. 战略背景

- **业务目标**：完善团队空间权限体系，使"角色 + 文件夹 + 分享"三层权限语义一致且可审计；降低越权分享风险。
- **为什么现在**：权限模型正处于重设计窗口（`20260814-permission-model/design.md`），单值枚举向权限点组合迁移，此时纳入文件夹增强与分享上限，可避免二次改造。
- **对齐约束**：云盘专项规则——文件权限安全、分享访问控制、数据一致性为硬约束；核心权限计算逻辑必须加中文注释。

## 5. 方案概述

### 5.1 权限点体系（沿用现有 JSON 键，9 个）

```json
view / upload / download / delete / rename / move / share / manage_members / manage_settings
```

- 隐含关系：`upload` 隐含 `view`；`download` 隐含 `view`（计算时自动补全）。
- `share`：发起分享所需权限点。
- `manage_members` / `manage_settings`：空间级管理权限点，仅管理员/管理角色持有。

### 5.2 角色模型

| 类型 | 说明 | 权限点示例 |
|------|------|-----------|
| 内置管理员（role=0） | 空间拥有者/管理员，不受文件夹规则限制 | 全部 true |
| 内置编辑者（role=1） | 现有预设 | view/upload/download/delete/rename/move/share true |
| 内置查看者（role=2） | 已确认：仅可在线查看 | view=true，download=false |
| 自定义角色（roleId≥100） | `team_role.permissions` JSON（已支持） | 任意组合，如"上传者"= view+upload |

### 5.3 文件夹权限 = 增强（并集）

- 主体类型：`all`（全体，管理员除外）、`member`（单用户）、`role`（角色，二期）。
- 规则挂在任意节点（文件夹或文件），对该节点及子树生效。
- 有效权限计算：

```text
用户对节点有效权限集 =
    空间角色权限集(roleId → team_role.permissions)
    ∪ 从节点向上遍历至空间根收集的文件夹规则权限集
管理员（roleId=0 或 manage_settings=true）：直接全部权限，不受文件夹规则限制
```

- 原"最近规则覆盖 / member 优先 role"改为"向上收集所有匹配规则取并集"（增强语义）。

### 5.4 分享权限上限

- 分享权限集 = 请求权限集，必须 ⊆ 用户对该文件的有效权限集，否则拒绝并提示"分享权限不能超过你的权限"。
- 发起分享需具备 `share` 权限点。
- `allow_download` 由权限集含 `download` 联动推导（含 → 1，否则 0），兼容前端开关。

## 6. 成功指标

### 主指标
- **权限配置操作成功率**：管理员保存文件夹/文件权限配置成功率 ≥ 99%，错误提示可理解。

### 次指标
- **权限生效正确率**：覆盖"角色 ∪ 文件夹规则并集"的集成测试全通过（含 Q4/Q6 用户例子）。
- **分享越权拦截率**：超出有效权限的分享请求 100% 被拒绝并提示。
- **管理效率**：管理员完成一次文件夹授权 ≤ 3 步交互（进入详情 → 选择主体 → 勾选权限保存）。

### 护栏指标
- 现有角色权限行为不回归（内置查看者/编辑者历史行为保持）。
- 分享下载开关（`allow_download`）行为不回归。

## 7. 用户故事与需求

### 史诗假设（Epic Hypothesis）

> 我们相信，为团队空间增加"文件夹权限配置（角色 ∪ 规则并集增强）+ 分享权限上限"后，管理员可以按文件夹精准授权、分享越权风险显著下降，因为权限粒度从全局角色细化到节点级规则，且分享权限受自身有效权限硬约束。

### 用户故事与验收标准

**Story 1：管理员为全体成员（管理员除外）配置文件夹权限**

- 摘要：让管理员一键为整个团队（管理员除外）增强某文件夹权限。
- **As a** 团队管理员
- **I want to** 在文件夹详情中对"全体成员"配置权限点
- **so that** 无需逐个成员配置，也无需改动全局角色

**验收标准（Gherkin）：**
- Scenario: 管理员对文件夹配置 all 规则
- Given 我是团队管理员（roleId=0 或持有 manage_settings）
- and Given 我在某文件夹详情页的权限配置面板
- When 我选择主体"全体成员（管理员除外）"并勾选 {download}
- Then 保存成功，该文件夹及子文件对该规则生效
- and Then 管理员本人不受该规则影响

**Story 2：管理员为单独用户配置文件夹权限**

- 摘要：按单个成员精准授权。
- **As a** 团队管理员
- **I want to** 针对某个成员单独配置某文件夹权限
- **so that** 该成员在授权文件夹内获得差异化能力

**验收标准（Gherkin）：**
- Scenario: 管理员配置 member 规则
- Given 我是团队管理员
- and Given 团队中存在成员"小明"（角色=上传者 {view, upload}）
- When 我在文件夹 A 的权限配置中选择"小明"并勾选 {download}
- Then 小明在文件夹 A 及子文件的有效权限 = {view, upload, download}
- and Then 小明在未配置的文件夹仍为 {view, upload}

**Story 3：用户有效权限 = 角色权限 ∪ 文件夹规则（并集增强）**

- 摘要：多规则命中取并集，不互相覆盖。
- **As a** 团队成员
- **I want to** 在命中的文件夹规则中获得增强权限
- **so that** 我的角色权限不会被文件夹配置覆盖或削减

**验收标准（Gherkin）：**
- Scenario: 同用户命中多条规则
- Given 小明角色权限 = {view, upload}
- and Given 文件夹 A 有 all 规则 {download}，文件 A/1 有 member 规则 {rename}
- When 小明访问文件 A/1
- Then 小明有效权限 = {view, upload, download, rename}
- Scenario: 管理员例外
- Given 我是管理员
- When 我访问任意文件夹
- Then 我拥有全部权限，不受任何文件夹规则限制

**Story 4：分享权限不超过自身有效权限**

- 摘要：分享越权硬拦截。
- **As a** 文件分享者
- **I want to** 仅能分享不超过自己对该文件有效权限的权限
- **so that** 我不会无意中把更高权限泄露给接收者

**验收标准（Gherkin）：**
- Scenario: 超限请求被拒绝
- Given 我对文件 F 的有效权限 = {view, upload}
- and Given 我具备 share 权限点
- When 我发起分享并请求权限 {view, upload, download}
- Then 请求被拒绝，提示"分享权限不能超过你的权限"
- Scenario: 合法请求成功且 download 联动
- Given 我对文件 F 的有效权限 = {view, upload, download}
- When 我发起分享并请求权限 {view, download}
- Then 分享创建成功，`allow_download` = 1

### 约束与边界

- 权限点隐含关系：`upload`/`download` 自动补全 `view`。
- `all` 规则对管理员无效；管理员拥有全部权限。
- 规则继承：挂在节点 → 该节点及子树（经父链收集）。
- 历史数据迁移：`team_folder_permission.permission` / `file_share.permission` 单值映射到权限点集合（具体映射见开放问题 O2）。

## 8. 范围外（Out of Scope）

- **显式禁止/拒绝规则**（如"禁止某用户下载"）：本次仅增强（并集），不做显式禁止；如确有需求作为独立增强项评估。
- **按角色主体配置**（`role` 主体）：数据模型预留，交互与规则收集作为二期。
- **防下载对抗**（截图/水印/浏览器插件对抗）：内置查看者 download=false 已确认，对抗手段不在本次范围。
- **权限审计与操作日志页**：本次仅做权限计算与校验，审计报表另行立项。
- **移动端适配优化**：沿用现有响应式，不做专项设计。

## 9. 依赖与风险

### 依赖
- 技术：`team_role.permissions` JSON（已存在）、`team_folder_permission` / `file_share` 表结构变更（迁移脚本 34/35）。
- 数据：H2 schema 同步 + `compare-schema.ps1` PASS + `schema_version` 登记。
- 协作：前后端接口契约以 design.md 的 API 章节为准；前端可先用 mock 并行开发。

### 风险与缓解
| 风险 | 影响 | 缓解 |
|------|------|------|
| 并集计算导致权限意外放大（如 all 规则误配 download） | 数据泄露 | 默认权限最小化；规则配置二次确认；集成测试覆盖组合场景 |
| 历史单值 → 权限集迁移映射错误 | 存量权限漂移 | 迁移脚本幂等守卫 + 迁移前后对比 + 全量测试 |
| 分享越权拒绝引起用户困惑 | 体验下降 | 明确错误提示文案；前端禁用超出自身权限的选项 |
| 权限计算性能（节点多、规则多） | 操作变慢 | 规则按节点索引、缓存角色权限集；上线前压测 |
