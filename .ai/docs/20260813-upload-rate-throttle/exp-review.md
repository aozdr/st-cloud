# 体验评审

> 落盘路径：`.ai/docs/20260813-upload-rate-throttle/exp-review.md`
> 归属 EXP_DESIGN（dependsOn: REQ_ANALYSIS）

# 一、体验目标

低速率强制限速场景下，用户上传体验应满足：
1. **可感知**：用户清楚知道「正在限速中转上传」而非假死
2. **可预测**：基于限速值给出预估剩余时间
3. **可中断**：暂停/取消在中转模式下同样可用
4. **无割裂**：中转模式与直传模式视觉表现一致，仅状态文案差异

# 二、评审结论：通过（附体验要点）

本任务核心为服务端逻辑，UI 改动集中在状态反馈，不新增页面、不改变现有上传面板布局。评审通过，以下为须落实的体验要点：

## 要点 1：状态文案区分（P0）

中转模式下任务卡片显示「限速中转上传中 · 限速 X KB/s」，区别于直传的「上传中」。避免用户在极低速率下误以为卡死。

## 要点 2：进度平滑推进（P0）

中转模式进度按服务端逐块确认的字节推进（非按 5MB 分片跳变）。低速率下用户能看到进度缓慢但持续增长，心理感知优于长时间停滞。

## 要点 3：预估剩余时间（P1）

中转模式速率可预测（≈限速值），展示预估剩余时间。极低速率下可能很大（数小时），格式化「Xh Ym」，>24h 显示「>24h」，避免显示一长串秒数造成焦虑。

## 要点 4：失败文案可操作（P1）

限速过低导致超时失败时，错误文案明确「传输超时，当前限速值过低」，引导用户调高限速或耐心等待，而非笼统的「上传失败」。

## 要点 5：暂停/取消一致（P1）

中转模式暂停/取消行为与直传一致：暂停即停止发送小块，取消即通知服务端清理临时文件 + abort multipart。

# 三、风险提示

- 极低速率（如 1KB/s）下上传 10MB 需约 2.8 小时，属合理预期但需明确告知用户，不可隐瞒。
- 中转模式不引入新色/新图标，复用现有 design system，避免视觉割裂（见 uispec）。

# 四、下游影响

体验评审通过后解锁 TECH_DESIGN（门禁：EXP_DESIGN 须先于 TECH_DESIGN）。程序设计须落实上述体验要点对应的前端字段与状态分支。
