# CR-02 团队自定义角色完整链路：需求

修订：design-v1；基线：912996e1；P0；需求完成，功能未实现。

## 现状与目标

TeamRole 使用 Long ID，TeamMember/TeamInvite 与 DTO 使用 Integer，数据库 team_member.role、team_invite.role 使用 TINYINT。前端 TeamMember/TeamInvite.role 为 number，邀请表单 parseInt 且仅支持三个预设选项。自定义角色无法完整进入成员、邀请和权限链路。

同时，TeamServiceImpl 的两个 checkPermission 重载只判断 level > min，legacyLevelOf(empty) 返回 -1；失效角色还有回退查看者路径。目标是使自定义角色可真实分配、精度不丢失、失效角色拒绝授权、无权限不能通过等级门禁。

## 用户与范围

管理员创建/修改角色、邀请用户、生成链接、修改成员角色；内部和外部成员按有效角色访问；访问者接受邀请；用户在搜索、目录和团队内容接口受到相同权限约束。

保留预设 0=管理员、1=编辑者、2=查看者；其他合法 ID 必须属于当前空间的启用自定义角色。保留角色权限与目录规则的既有并集语义，不将预设角色全部迁到 team_role，也不重构全局权限体系。

## 需求规则

- R02-1：角色引用在 Java/DB 使用 Long/BIGINT，HTTP 返回和前端内部统一十进制字符串。字段名仍为 role。
- R02-2：直接邀请、链接创建/接受、成员角色更新、外部成员访问和角色 ACL 匹配均支持自定义角色；接受链接时重新验证角色，不信任创建时校验。
- R02-3：空、负数、溢出、不存在、禁用、已删除、跨租户或跨空间角色不得授予默认查看权限。合法空权限自定义角色仍可叠加已有合法目录规则；最终有效集合为空则拒绝。
- R02-4：等级门禁明确拒绝 level<0；minRole/minPermission 为 null 不能把无权限变为许可。角色 ID 与旧权限等级为不同概念，不统一改为 Long 等级。
- R02-5：成员角色变更提交后，后续鉴权使用新角色；角色规则变更后不沿用旧结果。保持搜索最终输出前 fresh 复核。
- R02-6：已被成员或未过期有效邀请引用的自定义角色不能删除；同空间校验和预设角色不可删除约束先于删除操作。
- R02-7：空间所有者仍保持现有保护，不能通过成员角色更新取消其管理身份。外部成员有效期和空间外部协作开关不因类型迁移被绕过。
- R02-8：现有 UI 增加自定义角色选择与成员角色修改，保持原布局和权限入口；未知角色显示“角色已失效”，不能伪装为查看者。

## 验收标准

A02-1：大于 JS 安全整数的角色 ID 创建、邀请、分配、保存、读取后逐字符一致。A02-2：有 view 可查看，无 upload 且无目录授权时不能上传。A02-3：空权限、失效角色及跨空间引用不能绕过门禁。A02-4：角色切换与权限修改后下一次鉴权生效。A02-5：链接角色失效时接受失败，不新增成员。A02-6：成员、链接、角色与 ACL 页面正确回显名称、精度和失败状态。

## 数据/API 与兼容

扩容两张表的 role，既有 0/1/2 原值不迁义。请求兼容旧客户端传来的预设数字 0/1/2；自定义角色以字符串传输；响应统一字符串。旧客户端依赖 role===0 等比较，需要先发布兼容读取层，再切换后端和开启自定义分配。具体发布顺序见设计。

无未决产品问题；非法历史引用不自动改成查看者，需保留并以失效角色呈现。此轮不写数据迁移脚本，不修生产数据。
