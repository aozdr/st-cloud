# CR-03 团队复制目标写权限：需求

修订：design-v1；基线：912996e1；优先级：P0；状态：需求文档完成，功能未实现。

## 现状与目标

`st-team/src/main/java/com/stcloud/team/controller/TeamController.java` 的 `copyFiles` 对源节点和目标目录均调用 `requirePermissions(..., "view")`，随后进入 `FileServiceImpl.copyTeamFiles`。复制实际会创建节点、增加对象引用和空间用量。目标只有查看权限的成员不应获得该写能力。

目标是封住目标目录写权限缺口，同时保留已授权用户的服务器内部复制体验。

## 用户、场景与边界

用户包括团队成员、通过目录规则取得局部权限的成员及空间管理员。场景包括单文件、批量文件、目录复制，以及复制到空间虚拟根目录。只覆盖现有团队复制接口；个人复制、跨空间复制产品能力、下载权限定义不在本项范围内。

## 业务规则

- R03-1：每个源节点需要 `view`，目标目录需要 `upload`。不额外要求源 `download`；本次将服务器内部复制定义为现有内容操作。
- R03-2：源节点和目标目录必须满足既有空间归属、节点状态、目录类型和容量校验。根目录以现有 null/0 语义处理。
- R03-3：所有源权限和目标权限检查完成后才能开始复制。任一失败时整次请求不得创建节点、增加引用或容量、发布复制事件或记录成功活动。
- R03-4：有效权限由服务器计算，前端入口可见性不能代替服务器鉴权。
- R03-5：成功路径的命名冲突、引用计数、配额、搜索索引和同步事件语义保持现状，不引入新复制流程。

## 异常与验收标准

| 编号 | 可观察结果 |
|---|---|
| A03-1 | 源可查看、目标无 upload 时返回现有 TEAM_PERMISSION_DENIED，复制无副作用 |
| A03-2 | 源可查看、目标有 upload 时复制成功；根目录同样遵守规则 |
| A03-3 | 批量中一个源无 view 时整体拒绝，不出现前半批已复制 |
| A03-4 | 成功后的节点、对象引用、空间用量、搜索和同步事件与原有有效复制保持一致 |

## 数据、接口与风险

接口路径和请求响应结构不变；权限收紧属于漏洞修复，原本越权成功的请求将被拒绝。无 schema 变化。CR-02 会改变角色解析，但本项使用现有权限点 API，可先独立修复。常规复制事务不扩展为外部 S3 调用事务。没有需要用户裁决的未决产品事项。
