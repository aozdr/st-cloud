# CR-01 Access Token 撤权：需求

修订：design-v1；基线：912996e1；P0。本文完成需求定义，不表示修复已实施。

## 问题与目标

JwtAuthenticationFilter 直接采用 Token 中的 roles、permissions、dataScope。AuthService 在登录/注册/刷新时签发权限快照，管理端修改用户/角色后未建立 Access Token 版本校验。因此撤销权限后旧令牌仍可能授权请求。

目标：安全变更数据库事务提交后，之后开始鉴权的旧 Access Token 不再建立认证上下文；多个实例遵守同一判据。已经通过鉴权的在途操作不在本项中途撤销。

## 用户与场景

管理员禁用/删除用户、重置密码、分配用户角色、修改或删除角色及角色权限；普通用户登录、刷新、访问受保护 HTTP 接口；桌面同步客户端使用 Access Token 建立 WebSocket。当前已定位的密码修改入口为管理端重置，未来自助修改必须调用相同安全变更方法，本轮不新增自助改密功能。

## 业务规则

- R01-1：用户拥有单调递增的 securityVersion。用户状态或密码、角色成员关系、有效角色权限/状态/dataScope 改变时，在同一数据库事务内递增相关用户版本。
- R01-2：认证核对签名、过期、令牌用途、租户和用户归属、用户/租户可用状态、当前安全版本；不存在、已删除、禁用或版本不一致均拒绝。
- R01-3：签发的权限集合和版本必须来自同一数据库一致性快照，不能出现旧权限配新版本。
- R01-4：数据库不可用时拒绝建立认证上下文。第一版直接读取主库，不使用可能陈旧的 Redis 安全版本缓存。
- R01-5：Refresh Token 仍使用现有 Redis 登记和吊销机制，同时绑定安全版本，避免改密/撤权与刷新交错重新获得有效权限。安全版本变化后需要重新登录，不承诺静默刷新保留登录态。
- R01-6：已有 download/editor 用途令牌的端点、节点绑定和短期有效语义保持不变，不把它们作为普通 Access Token 校验；不能使用 refresh/download/editor 令牌建立同步 WS 或访问普通业务接口。
- R01-7：缺少版本字段的旧 Access/Refresh Token 不按 0 放行。升级切换后要求重新登录。令牌签名密钥和原有效期不因本项改变。
- R01-8：新 WS 握手执行相同校验。已建立连接在下一次接收消息或发送业务消息前复核版本与到期时间，失败关闭；不新增推送协议或扫描所有连接的分布式任务。

## 验收结果

| 编号 | 结果 |
|---|---|
| A01-1 | 禁用、删除、重置密码提交后，旧 Access Token 新请求被拒绝 |
| A01-2 | 撤销 ADMIN、删除角色、停用角色、删除权限后，相关用户旧 Token 被拒绝 |
| A01-3 | 版本未变、用户/租户正常时正常访问；无关用户不会被批量误撤权 |
| A01-4 | 刷新被吊销或版本过旧时不签发有效新会话；签发与权限变更并发不混配权限和版本 |
| A01-5 | 流式专用令牌原有约束保持；WS 不形成 Access 校验旁路 |

## 范围与影响

涉及 st-common、st-auth、st-admin，以及 st-sync 已有鉴权入口；增加 sys_user 字段和测试 schema。无新会话平台，无全 Controller 手工失效逻辑，无本次无关 RBAC 重构。HTTP 登录响应结构不变，JWT 内部声明扩展。直接主库读取会增加每次认证数据库读量，作为撤权正确性的明确代价。

本方案选择升级重新登录与数据库权威校验，不留下常规技术选择待用户裁决；实施/发布授权不由本文替代。
