# CR-04 跨同步根移动一致性：需求

修订：design-v1；P0；当前基线 912996e1；未实施。

## 现状

SyncServiceImpl.delta 对 MOVE/RENAME 同时要求 path 和 oldPath 在 root 内，导致移入与移出均被过滤。SyncChangeEvent 已有 oldPath/oldParentId，两个日志消费通道保存 oldPath；SyncChangeLog 没有 oldParentId。客户端目录 CREATE 仅创建目录，不拉取子树；downloadFile 捕获错误不抛出，可能让游标在失败后推进。fullReconcile 只补缺失与内容差异，不能把历史移出留下的文件清走。

## 目标、用户与边界

桌面同步用户将文件或目录在云端同步根内部、外部之间移动后，在网络恢复并同步成功时，本地受管理内容和云端有效范围一致；本地独立修改必须保留，不能为追求一致直接删除用户数据。

有效范围定义为根目录内部且不位于排除路径；根 A 与根 B 对同一次移动独立投影。只处理已有移动/重命名链路及直接相关的消费、重试和升级恢复，不重建整套同步协议、不改上传分块算法。

## 规则

- R04-1：旧内新内→MOVE/RENAME；旧内新外→DELETE；旧外新内→CREATE；均在外→不输出。转换由服务端执行，客户端不猜测根外绝对路径。
- R04-2：DELETE 的 path 必须为旧根内相对路径；CREATE 的 path 为新相对路径，oldPath 清空；不得把根外路径交给本地文件系统。
- R04-3：目录移入必须补齐有效子树，移出必须处理受管理后代和状态；目录 mtime 不能证明全部子文件未修改。
- R04-4：分页按扫描过的日志推进，不按输出条数推进；全部被过滤的页仍可继续。客户端只有当前批次处理成功或安全记录冲突后才能固化游标。
- R04-5：重放、断网、下载失败、应用退出后重试不能导致永久遗漏或误删。根 A 的状态修复不得清空根 B。
- R04-6：本地改动或不明归属内容保留为可恢复副本；不能移出后又自动上传到旧位置。
- R04-7：升级时修复仍有同步状态依据的历史跨根残留。对已失去状态、无法区分本地原创与残留的文件，不自动删除；在现有同步错误/历史界面提示需人工核对。
- R04-8：用户/租户/根所有权、路径边界和排除规则保持严格。同步根节点本身移动不视为“删除本地根”，根身份以 cloudFolderNodeId 为准。

## 验收结果

A04-1：文件/目录四态投影正确。A04-2：文件夹移入后完整子树可用，移出不残留受管理旧路径。A04-3：失败不推进游标，重复应用不重复生成文件或反向删除云端。A04-4：排除边界和两个根互不污染。A04-5：历史修复保存用户独立修改，不 reset 全部本地数据库。A04-6：未知/缺失 oldPath 与无效本地路径明确失败或进入对账，不静默跳过后宣称成功。

## API、数据与风险

复用 CREATE/MOVE/RENAME/DELETE 事件类型，不新增 MOVE_IN。delta 响应增加可选 scopeProjectionVersion=2 和 reconcileRequired，旧客户端忽略，升级客户端据此识别服务端能力和必要对账。服务端日志 schema 不变；桌面升级恢复使用现有 root syncVersion/cursor 和本地恢复清单。跨版本协调、目录规模和事件后再次移动的竞态在设计中处理。

无待用户决定的常规方案；无法证明归属的历史文件不纳入自动删除承诺。此轮只做设计。
