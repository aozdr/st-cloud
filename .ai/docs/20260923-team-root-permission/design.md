# 空间根目录权限修复设计

## 目标、用户与场景

空间管理员在“空间根目录权限”面板保存 all/member/role 规则。页面将根目录编码为 `nodeId=0`；当前服务把它作为 `file_node` 查询，返回“节点不属于该空间”。完成后，管理员可读回规则，普通成员在本空间节点上获得规则并集中的内容权限。

## 边界与规则

- `0` 仅表示已通过管理员校验的当前空间虚拟根目录；正数节点仍必须存在、正常且属于该空间。负数和其他空间节点拒绝。
- 内容操作的可选 `parentId=null` 同样表示当前空间根目录，权限校验统一映射到 `0`；直接查询 `resolveMyPermissions(spaceId, null)` 的角色权限语义保留。
- 根规则存储在现有 `team_folder_permission`，以 `(space_id, folder_node_id=0)` 确定范围；读取及全量覆盖删除均带 `space_id`，避免同租户其他空间数据受影响。
- 解析正常节点时必须先核实完整父链到根。到根后把当前空间根规则并入角色及祖先规则；普通及 fresh 核权在父链断裂、循环、跨空间时均拒绝。
- 规则只增强内容权限，现有 `all` 不得包含空间管理权限的校验不变。管理员直通和非成员拒绝不变。

## 异常、数据与 API

- API 路径和响应格式不变；`/api/team/{spaceId}/folder/0/permissions` 从失败变为可用，向后兼容。
- 不变更表结构、不迁移或删除现存业务数据；根规则为空时沿用角色权限。
- 数据库查询范围增加 `space_id` 条件，可能多一次根规则读取；请求内 fresh 缓存复用该读取。

## 风险与验证

根规则属于权限放大路径。用集成测试覆盖保存/读回、跨空间隔离、成员可用和非管理员拒绝；用 fresh 测试覆盖正常父链与断链不放权。无需用户裁决的未决范围或兼容性问题。
